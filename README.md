# TG → 光鸭 · sbtg2cloud

在 Unraid（amd64）中运行的 Telegram 分享监听与光鸭云盘自动转存服务。中文 Web 管理页，Telegram 用户账号扫码、光鸭扫码、按频道选择目标目录，文件只在云端转存。

## 已实现的行为

- 支持消息正文、隐藏文本超链接、URL 按钮中的 `guangyapan.com/s/…` 分享链接。
- 仅监听勾选的频道和群。首次启动、重启及断线恢复均不扫描历史消息，不补抓离线期间消息。
- 所有已入队任务保存在 SQLite 中；恢复运行后继续处理。
- 转存分享顶层全部文件/文件夹，保留其内部结构。每个来源可指定目录，也可以继承默认目录。
- 分享 ID 全局去重：同链接不会因来自不同频道而重复转存；成功后不追踪分享新增文件。
- 提取码从 URL 参数或同一消息文本识别；失败任务可手动补码和重试。
- 失效分享可点击“丢弃”：仅限失败或结果待核对的任务，确认后从“需要处理”移除，保留记录、原错误和云端回执，可用“已丢弃”筛选查看。丢弃的分享仍全局去重，不再入队、重试或补全名称；不删除云盘文件，也不撤销已经发生的云端转存。
- “需要处理”筛选中可点击“一键丢弃需要处理”，确认数量后跨全部分页处理；只处理确认时的任务清单，新出现的失败任务、已恢复的任务和有关联清理操作的任务会跳过。
- 同一筛选中的“一键重试”支持跨页重新排队，保留原保存目录和提取码，沿用后台限速。包含“结果待核对”时，必须额外确认这些任务尚未转存，避免重复保存。只重试确认清单中仍失败或待核对的任务，已成功、已丢弃、处理中或有关联清理操作的任务会跳过；不会重新扫描 Telegram 历史消息。
- 临时读取错误最多尝试 3 次；实际转存请求结果不明时暂停，要求核对云盘后手动重试。
- 到期的排队/重试任务与已提交任务的进度查询交替调度，各类内部仍按时间排序；一类没有到期任务时继续处理另一类，避免大量进度查询长期挡住重试。仍使用同一个后台工作器和云盘请求限速。
- 普通目录分页按接口的 `total` 判断是否读完，兼容恰好 100、200 等整页数量的目录，避免多读末尾空页而误报列表无法识别；分享链接的游标分页仍按原协议处理。
- “需要处理”表示执行失败或提交结果不明，不等于分享失效。分享读取和保存目录核对均对临时网络/限流错误最多尝试 3 次，至少间隔 60 秒；登录失效、接口解析或目录校验失败保留具体原因。正常分享也可能因自己的云盘登录失效、保存目录无法读取而转存失败。升级不会自动重试或丢弃已有失败任务。
- 提交转存后轮询云端任务，只有确认完成才显示“已完成”。进度查询暂时失败不会重新提交。
- 不发送 Telegram 消息，不点击回调按钮、不访问短链或第三方跳转站。
- 可选 Emby 光鸭 302 播放入口：保留 MediaTidy 整理、现有 STRM 和原 Emby 账号，针对光鸭挂载目录的原画请求获取临时直链并跳转，首批以 SenPlayer 为验证目标。

## Unraid 部署

将本项目源代码放到 Unraid 的一个目录，例如 `/mnt/user/appdata/sbtg2cloud-src`。源码目录和运行数据目录请分开。以下在 **Unraid 终端**执行。

### 方式一：Docker Compose

需要 Unraid 已有 Docker Compose 命令（可通过 Compose Manager 使用）。

```sh
cd /mnt/user/appdata/sbtg2cloud-src
cp .env.example .env
```

编辑 `.env`，将 `BIND_IP` 改为 Unraid 的实际局域网 IP，确认 `APPDATA_PATH`。默认以 Unraid 的 `nobody:users`（99:100）运行。

```sh
install -d -m 700 -o 99 -g 100 /mnt/user/appdata/sbtg2cloud
docker compose up -d --build
docker compose logs --tail=100
```

浏览器打开 `http://你的Unraid局域网IP:8080`。未设置 `.env` 时端口默认绑定所有网卡，建议明确设置 `BIND_IP`。此服务没有管理密码，不做公网端口映射。

### 方式二：Unraid 自带 Docker，无需 Compose

```sh
cd /mnt/user/appdata/sbtg2cloud-src
install -d -m 700 -o 99 -g 100 /mnt/user/appdata/sbtg2cloud
docker build --platform linux/amd64 -t sbtg2cloud:local .
```

在 Unraid Docker 页面“添加容器”，填写：

| 项目 | 值 |
| --- | --- |
| 名称 | `sbtg2cloud` |
| Repository | `sbtg2cloud:local` |
| Network Type | `bridge` |
| WebUI | `http://[IP]:[PORT:8080]` |
| 端口 | 容器 `8080` → 主机 `8080`，TCP |
| 可选播放端口 | 容器 `8081` → 主机 `12359`，TCP；同时添加环境变量 `EMBY_PROXY_LISTEN_PORT=8081`、`EMBY_PROXY_PORT=12359` |
| 数据路径 | 容器 `/data` → 主机 `/mnt/user/appdata/sbtg2cloud`，读写 |
| Extra Parameters | `--user 99:100 --restart unless-stopped --security-opt no-new-privileges:true --cap-drop ALL` |

镜像包含健康检查。数据目录应只允许服务用户和管理员访问。

## SenPlayer / Emby 光鸭 302 播放

本功能作为播放入口使用，不代替 MediaTidy 整理，不改写已有 STRM，也不接管 Emby 媒体库。默认关闭。Compose 增加容器 `8081` 的端口映射；主机端口由私有 `.env` 的 `EMBY_PROXY_PORT` 配置，默认 `12359`。升级旧 Compose 时需保留原数据卷、管理端口和 Telegram 代理，增加这个端口及 `EMBY_PROXY_LISTEN_PORT=8081` 后重建容器，单纯重启不会增加映射。两个 HTTP 入口共用同一进程、SQLite、光鸭会话和云盘限速，不启动第二个转存实例。

在管理页的“Emby · 光鸭 302 播放”填写并保存：

| 配置 | 含义及示例（自行替换） |
|---|---|
| Emby / MediaTidy 上游地址 | 可访问的完整 HTTP 地址，例如 `http://emby.example:8096`。若已有 MediaTidy 反代，填其现有播放地址可保留其他网盘的原链路。不可填 sbtg2cloud 自己的地址，不需要填写管理员 API Key。 |
| Emby 中的光鸭挂载路径 | Emby 返回的实际视频路径前缀，例如 `/CloudNAS/CloudDrive/光鸭云盘`；应使用 STRM **内容指向的路径**，不是存放 STRM 文件的 `/strm` 目录，也不是 MediaTidy 容器内的整理路径。 |
| 光鸭内对应目录 | 上述挂载路径在光鸭内对应的目录，整盘挂载一般填 `/`。例如只挂载电影目录，则填 `/Media/电影`。 |

例如 Emby 中的视频路径为 `/CloudNAS/CloudDrive/光鸭云盘/Media/电影/示例.mkv`，映射后就是光鸭内的 `/Media/电影/示例.mkv`。只接受目录边界内的精确名称匹配，不按相似片名猜测；同名歧义、已移动/删除或类型不符会停止取链并显示错误。

在 SenPlayer 添加 **Emby** 服务器，地址填 `http://你的Unraid局域网IP:12359`（以页面显示和实际映射为准），使用原来的 Emby 用户名和密码。可以另存为一个新服务器入口，保留原连接方便对比。海报墙、登录、播放进度、字幕及 WebSocket 控制请求继续转发给上游；不要将这个地址当作光鸭分享链接或新增网盘账号。

客户端请求 `/Videos/{id}/original.*` 或显式 `Static=true` 的 `/Videos/{id}/stream.*` 时，服务使用**该客户端的 Emby 凭据**重新查询 PlaybackInfo。通过 Emby 检查后才定位光鸭文件 ID，调用下载接口并返回 `302 Location: <signedURL>`。客户端直接向光鸭 CDN 读取视频和 Range 分段，sbtg2cloud 不读取这些视频字节。HLS、字幕烧录及需要转码的请求保留上游处理，不强制修改客户端能力或关闭转码。其他网盘及未匹配光鸭前缀的资源仍沿用上游播放链路。匹配光鸭但取链失败时返回明确错误，不悄悄回退成 NAS 中继；可使用原播放入口恢复原链路。

为减少光鸭访问，不在浏览海报墙或定时任务中预取直链。播放时逐层查目录，目录列表只在内存缓存 5 分钟；缓存没有新文件时单独刷新其父目录。直链及记录在 SQLite 中持久缓存，不同 Emby 用户以及容器重启后均可复用。**记录保留时间与直链可复用时间一致**：按光鸭返回的 `urlDuration` 计算，并提前预留 5 秒余量，不再使用固定的一天保留期限或一天上限。已有记录升级时同步为原直链的到期时间，不重新取链、不延长原签名。到期后记录在下次本地列表读取或缓存写入时移除，只在下次播放重新取链，不额外访问云盘。

管理页的“直链缓存 · 随链接到期”显示资源路径、获取时间、缓存及记录共用的到期时间、命中次数、最近使用时间，每页 20 条。页面轮询只读本地缓存信息并清除超期缓存记录，不生成直链或探测 CDN。命中次数统计 GET/HEAD 等请求，并非观看人数。链接提前失效或同名文件替换后，可点击“清空直链缓存”，然后重新播放；清空只影响本地缓存，不删除云盘文件，也不能撤回已经交给播放器的链接。列表和管理 API 不返回完整的签名直链。

每次 302 仍重新检查该客户端的 Emby 凭据，不缓存用户授权；同时发起的拖动或多用户请求合并取链。光鸭令牌自动续期会保留缓存；重新扫码或切换会话则原子地更新缓存归属并清空旧缓存，避免跨账号复用。所有光鸭 API 请求沿用原有串行锁、两秒间隔及限流退避。首次深层目录取链可能需要十几秒，45 秒仍未完成则报超时；已缓存直链对应文件的改名、同名替换或删除不主动探测，应按需清空缓存。

多个用户命中同一缓存后，分别向 CDN 发起自己的下载和 Range 请求：缓存节省的是取链接口访问，不合并视频流量，也不意味着只消耗一份网盘流量。服务端授权通过不代表光鸭一定允许任意设备、出口 IP 或并发数；实际限制、速度和提前失效规则由光鸭控制，本项目不绕过这些限制。缓存内的完整直链同样属于私有运行数据，随 `/data/state.sqlite3` 保存并保持文件权限，不得将数据库、备份或真实直链上传 GitHub。

页面显示本次运行的 302 次数、最近资源及最近错误，不显示临时直链或登录令牌。两个入口都关闭访问日志；不要自行开启 HTTPX、WebSocket 或反代的原始请求调试日志，以免记录 Emby Token 或下载签名。管理页仍只适合可信局域网，不得将无密码的管理端口暴露公网。

验证时选择一部已有光鸭影片，在 SenPlayer 起播、拖动进度，检查管理页“本次运行已返回 302”及“最近”资源。仅登录成功、海报墙正常或 Emby 显示“直接播放”，均不能单独证明视频绕过 NAS。账号权益、取链接口限速以及客户端跟随跳转的能力仍需实际播放确认。自动清理配置不受本功能影响；被清理的云端资源无法继续作为长期媒体库使用，归档目录需与待清理目录分开。

## 仅 Telegram 使用代理，光鸭直连

推荐部署方式为 **Telegram 走 HTTP CONNECT 代理，光鸭直连**。仅支持 HTTP CONNECT；没有实现或验证 SOCKS5、SOCKS4、MTProxy，也不接受 `https://` 代理协议。未填写 Telegram 代理地址时，Telegram 也保持直连。

在项目 `.env` 中按需填写（示例主机需自行替换，不要提交真实地址或密码）：

```env
TELEGRAM_PROXY_URL=http://proxy.example:8080
```

- `TELEGRAM_PROXY_URL` 显式传给 Telethon；不配置则 Telegram 直连。它不读取 `HTTP_PROXY`、`HTTPS_PROXY` 或 `NO_PROXY`。
- Compose 明确清空容器内的 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 及对应小写变量，并设置 `NO_PROXY=*`、`no_proxy=*`，保证光鸭 HTTPX 请求直连，避免 Docker 客户端的默认代理设置影响光鸭。无需在 `.env` 中配置这些通用代理变量；旧 `.env` 若有这些配置可以删除，当前 Compose 不再引用它们。
- `NO_PROXY` 不影响 Telethon，所以光鸭直连不会绕过 Telegram 的显式代理。本示例使用 `*` 表示全部 HTTP 请求直连，不依赖 CIDR 网段匹配能力。
- 建议显式填写代理端口；Telegram 未指定端口时默认 8080。
- 带认证时使用 `http://用户名:密码@主机:端口`。用户名、密码必须非空；`@`、`:`、`#`、`%` 等特殊字符按 URL 规则编码，例如 `http://user%40domain:p%40ss%3Aword@proxy.example:8080`。若 Compose `.env` 的值含字面 `$`，使用单引号包裹该值，避免变量插值。

Compose 只从 `.env` 读取 Telegram 代理地址，代理设置仅作用于 **sbtg2cloud 这一个容器**，不更改宿主机或其他容器。不要把真实代理地址写入源码或 Dockerfile。在 Unraid Docker 模板部署时，添加 `TELEGRAM_PROXY_URL`，将通用代理变量（含小写及 `ALL_PROXY`）清空，并设置 `NO_PROXY=*`、`no_proxy=*`，效果相同。

升级代码/依赖后执行：

```sh
docker compose up -d --build --force-recreate sbtg2cloud
```

只修改代理环境变量时也必须重建容器，单纯 `docker restart` 不会加载新环境。原 `/data` 挂载保持不变；不要删除会话、重置数据库或同时启动第二个实例。

配置错误会在 WebUI 显示具体字段及原因，不回显 URL 或认证信息；不会悄悄改为直连。普通连接失败按原有间隔每 10 秒重试。Telethon 有时会把底层超时/代理握手异常归并为通用连接错误，此时页面会说明正在通过 HTTP 代理连接，并提示检查可达性、CONNECT 支持和认证，不能保证总能精确判别 407 或超时。SDK 原始日志已禁用，避免协议请求或异常携带敏感数据；页面只显示经过处理的固定错误提示。

验证范围：测试覆盖无代理、HTTP 代理、百分号编码认证、非法配置、失败后重试、HTTPX 环境代理和精确 `NO_PROXY` 匹配，并用本地 HTTP CONNECT 服务验证 PySocks 实际握手及认证。用户现场报告已验证原会话恢复连接、光鸭目录和既有配置/历史保持不变；本次未访问现场代理，也未用新分享验证完整自动转存链路。

## 初始化

1. 打开 [my.telegram.org/apps](https://my.telegram.org/apps)，申请自己的 Telegram 应用，填写 **API ID / API Hash**。这是应用凭据，不是 Bot Token；扫码登录也需要它们。
2. 在管理页保存凭据，生成 Telegram 二维码，通过手机 Telegram 的“设置 → 设备”扫码。如账号启用两步验证，输入密码完成登录。密码不落盘；二维码过期后手动重新生成。
3. 生成光鸭二维码，用光鸭 App 扫码授权。登录令牌会自动续期，失效时重新扫码。
4. 选择默认保存目录；点击“编辑监听 → 获取聊天列表”，勾选频道、配置目录，然后点击“保存监听”。保存后仅显示选中频道，再次点击“编辑监听”可修改；取消会丢弃本次未保存的选择。
5. 等待选中频道发布新的测试分享，在记录中检查“云端处理中 → 已完成”，再去光鸭核对目标目录。

不会回溯旧消息，可在已加入且有发言权限的测试群中发布自己拥有的小文件分享，测试正文、按钮和提取码三种形式。目录选择器选择现有云盘目录；需要新目录时先在光鸭中创建。

转存记录优先显示消息中的资源名称，缺少时使用分享的文件/文件夹名称；一条消息有多个不同分享时分别使用各分享文件名。旧版记录没有保存片名，可点击“补全本页名称”读取原分享名称，此操作不会重新转存；失效或无法访问的分享暂不能补全。

转存记录默认每页 20 条，可选择 10、20、50、100 条，通过上一页、下一页或输入页码跳转。修改每页数量会返回第一页。“最新记录”返回第一页并获取新任务；浏览后续页时固定记录范围，避免新任务插入导致翻页重复或漏项，任务状态仍会刷新。

点击顶部“待处理”会跳转至转存记录并筛选排队任务；点击“需要处理”会筛选失败和结果待核对的任务。筛选覆盖全部记录，支持分页和自动刷新；通过记录区域的“记录筛选 → 全部记录”恢复查看。筛选中的任务状态变化后会移出或加入对应列表。

## 更新现有部署

用新版源码覆盖旧源码目录，保留 `.env` 和原 `/data` 挂载。Compose 部署执行 `docker compose up -d --build`；Unraid 模板部署重新执行 `docker build --platform linux/amd64 -t sbtg2cloud:local .` 后，在模板编辑页面应用配置以重建容器。仅重启旧容器不会换成新镜像。

新版本启动时自动添加资源名称字段，保留原登录、监听配置、任务和去重记录。建议更新前停容器并备份数据目录。

## 数据与恢复

`/data/state.sqlite3` 保存配置、光鸭令牌、来源和任务；`/data/telegram.session` 保存 Telegram 会话。它们是敏感登录凭据，不要上传到 Git、日志或公开聊天。备份前停止容器，并备份整个 `/data`（包含可能的 SQLite WAL 文件）。

任务状态：`queued` 排队、`preparing` 读分享、`submitting` 提交中、`submitted` 云端处理中、`success` 完成、`failed` 失败、`uncertain` 结果待核对。

- 修改目录只影响之后入队的任务；任务保存入队时的目标目录快照。
- 停用来源只停止接收，不取消已入队任务。
- 若在提交请求中途崩溃/超时，恢复后显示“结果待核对”，避免重复转存。检查云盘确定未转存后再重试。
- 云端任务明确失败时，先核对是否部分文件已保存，再手动重试；同名文件如何处理由光鸭服务决定，本项目不会主动删除或覆盖已有文件。
- 退出 Telegram 仅注销本项目会话，并停用来源，不注销手机等其他设备。
- 当前按单 Telegram 账号和单光鸭账号使用；更换光鸭账号前应停止监听并处理完队列，因为现有目录 ID 属于原账号。
- Telegram 消息时间戳精度为秒，启用/恢复监听同一秒的边界消息可能被接收，不扫描历史接口。

## 删除配置与自动清理

“删除配置”支持设置 **5～600 分钟的整数等待时间，默认 60 分钟**。点击“保存等待时间”写入本地数据库，容器重启保留。设置统一用于新任务与历史任务，对尚未提交的清理立即生效；缩短时间可能使现有任务立即到期，延长时间会推迟尚未提交的删除。

另可设置 **删除处理间隔 5～600 秒，默认 30 秒**（数据库变量 `cleanup_interval_seconds`），点击“保存删除间隔”后无需重启。此间隔控制自动清理每轮核对、提交删除或查询回执之后的最小等待；目录读取和网络耗时另计，已提交任务仍保留原回执查询间隔和失败退避，不会重复删除。云盘请求仍至少间隔 2 秒，限流时继续退避。该设置不影响手动清空。

“查看待清理任务”或记录筛选中的“待清理 / 清理中”覆盖全部分页；自动清理区域同时显示全库排队数量。记录按原任务编号排序，旧任务重试成功后仍在较早的分页，因此首页可见的待清理数量可能少于队列总数。

同一区域显示上一个清理完成的资源、当前核对/提交/等待回执的资源，以及下一个待清理资源，随页面自动刷新。只有云端成功回执才记为完成；新完成记录保存确认时间，旧记录没有该时间时明确标注。下一项按当前到期时间、失败退避与队列顺序推算，暂停时标记为暂停。显示仅读取本地数据库与后台正在处理的任务，不额外请求云盘。

管理页面底部提供“自动清理”开关，默认关闭。资源直接保存到你选定的目录，不创建额外的 `sbtg-*` 子目录。原监听配置和去重记录保留。

- 以本地 `completed_at`（确认云端转存成功的时间）为准，达到配置的等待时间后才允许清理。每 30 秒只查本地数据库，每轮最多处理一个任务；重启继续原计时。关闭开关暂停未提交的删除，已提交的删除无法撤回。
- 转存前记录目标目录已有 ID 和分享顶层条目的名称、类型、大小；成功后仅匹配本次新增且与分享条目一致的 ID。已有同名资源、合并、重命名或匹配不唯一时，保留转存结果并停止自动清理。不会删除选定的保存目录或其中原有资源。
- 为目标记录内容快照，到期后核对位置、名称和内容再删除。允许内部文件或子目录减少（包括全部移走后留下空目录），剩余条目的 ID、父目录、名称、类型及已记录的内容字段必须与原快照一致；新增、修改、替换、移动仍停止清理。目标目录本身必须仍在原位置且名称一致。操作期间不要由其他程序同时新增同名资源或修改目标；云盘没有已核实的原子条件删除接口，核对与删除之间仍有并发修改窗口。
- 普通文件或文件夹移入回收站，不清空回收站。删除超时、回执缺失或提交中重启时停止重发；有任务 ID 时只查询原任务。同一目标 ID 登记到单个清理任务，防止重复删除。
- 旧版已经生成的空 `sbtg-*` 目录不会继续作为重试的保存位置，也不会擅自删除。旧临时目录有内容时阻止重试，先核对资源；已经完成的旧任务保持原位置，不自动迁移内容。

历史成功记录没有 `completed_at` 时，按 `当前时间 - created >= 等待分钟数 × 60` 判断到期，不使用 `updated`。在“历史记录清理”中选定对应的实际文件或文件夹后，后台按该规则核对并移入回收站；仅处理成功任务。由于旧记录没有保存目标 ID，需要先选定目标，不能仅凭同名自动绑定。失败、未到期、未匹配或尚未选定目标的任务不会删除。开关关闭时已加入的清理任务暂停。同一文件 ID 只允许加入一次，删除失败或回执不明不会再次提交。

历史列表采用纵向卡片，显示创建时间、按配置计算的到期时间、原目录、候选名称和 ID。未到期任务不请求云盘；到期候选列表仅在点击时加载，同目录缓存 5 分钟。真正删除前重新核对，不使用缓存。

所有光鸭请求在单进程内串行发送，每次请求结束后至少间隔 2 秒；HTTP 429/5xx 至少冷却 60 秒，数字形式 `Retry-After` 按 60～900 秒处理。转存首次进度查询等待 15 秒，未完成时每 30 秒查询；删除进度最多每 60 秒查询一次（首次等待 30 秒）。页面常规状态刷新只读取本地状态。限速不能保证规避平台未公开的风控，请控制监听数量与任务量，保持单实例运行。

此功能已通过模拟协议测试，尚未用真实账号执行删除验证；默认保持关闭，先使用专门的测试资源验证转存、到期和回收站结果。

对于已经逐项确认的历史目录，提供独立工具 `scripts/cleanup_confirmed.py`。确认清单 JSON 使用 `{"version":1,"targets":[{"id":"目标目录ID","name":"目录名称","parent_id":"原父目录ID"}]}`，只支持目录。必须先停止主容器，使用同一数据卷运行，默认只读核对，显式传入 `--execute` 才整批移入回收站。工具使用实际目录 ID 与名称核对，不猜测历史成功时间；回执保存在 `/data/confirmed-cleanup.sqlite3`。相同清单再次执行只查原任务或报告原结果，出现部分重叠的新清单也会阻止重复删除。切勿删除该日志后重跑。操作期间不要同时在其他设备移动或删除目标目录。确认清单、执行日志和真实数据不得上传 GitHub。

## 一键清空转存目录

自动清理的只读核对遇到网络超时或限流时，保留待清理状态，至少等待 5 分钟后再核对；删除已经提交后的超时仍不会重发。目标不存在、移动、改名、新增或修改会停止删除并显示具体分类。升级后，一次性将旧版因快照差异/核对失败而停止、保留原快照且从未提交删除的记录恢复为待核对；仍需达到等待时间、启用自动清理并通过新规则后才删除。已提交、结果不明、一键清空占用的目标不会重新入队。原快照不被覆盖。

一键清空取得云端成功回执后，按实际目标 ID 同步对应的自动清理记录为“已移入回收站”；仅部分覆盖、结果不明或尚无成功回执时，不标记为完成。升级时也会根据本地已有成功回执补齐状态，不额外访问云盘。

预览失败原因直接显示在弹窗内；后台目录读取最多等待 45 秒，浏览器等待最多 50 秒。超时不会提交删除或自动重试，可稍后重新预览。切换目录或关闭弹窗会作废当前预览请求的结果。

在“删除配置”点击“一键清空转存目录”，选择已配置的转存目录，预览顶层文件和文件夹数量、名称后，点击“确认全部移入回收站”。此操作不受自动清理开关和等待分钟数限制，包含手动放入的资源以及文件夹内全部内容，保留选定目录本身。根目录不提供清空入口。

预览五分钟内有效，确认时固定目标 ID；预览后新增的顶层项目不会追加删除。执行前重新核对普通目录中的目标，位置、名称、类型或大小变化则停止。不要同时用其他客户端移动、删除目标或向其内部写入文件。最多每批 100 个顶层目标，批次串行执行；云端进度最多每 60 秒查询一次，页面刷新只读取本地进度。

已有云端转存或自动删除正在处理时，不能发起清空。清空期间新消息仍可入队，但暂停执行转存和自动删除。每批提交状态、云端任务 ID 持久化；重复确认不会重发，提交超时或中断后显示“结果待核对”，有任务 ID 的批次只查询进度。部分批次完成后出错会停止剩余批次，请先核对云盘。转存历史记录和去重记录不会清空。与该目录重叠的待自动清理任务会停止，避免再次删除。

## 本地开发及测试

Python 3.12：

```sh
python -m venv .venv
# 激活虚拟环境后
pip install -r requirements.txt
python -m unittest discover -s tests -v
node --test tests/test_clear_ui.cjs
```

Windows 可使用 `.venv\Scripts\python.exe`。默认本地数据目录 `./data`，可用 `DATA_DIR` 覆盖。必须单 worker 运行，不能启用多个 Uvicorn worker 或同时运行共享 `/data` 的容器。
