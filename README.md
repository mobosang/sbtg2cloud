# TG → 光鸭 · sbtg2cloud

在 Unraid（amd64）中运行的 Telegram 分享监听与光鸭云盘自动转存服务。中文 Web 管理页，Telegram 用户账号扫码、光鸭扫码、按频道选择目标目录，文件只在云端转存。

## 已实现的行为

- 支持消息正文、隐藏文本超链接、URL 按钮中的 `guangyapan.com/s/…` 分享链接。
- 仅监听勾选的频道和群。首次启动、重启及断线恢复均不扫描历史消息，不补抓离线期间消息。
- 所有已入队任务保存在 SQLite 中；恢复运行后继续处理。
- 转存分享顶层全部文件/文件夹，保留其内部结构。每个来源可指定目录，也可以继承默认目录。
- 分享 ID 全局去重：同链接不会因来自不同频道而重复转存；成功后不追踪分享新增文件。
- 提取码从 URL 参数或同一消息文本识别；失败任务可手动补码和重试。
- 临时读取错误最多尝试 3 次；实际转存请求结果不明时暂停，要求核对云盘后手动重试。
- 提交转存后轮询云端任务，只有确认完成才显示“已完成”。进度查询暂时失败不会重新提交。
- 不发送 Telegram 消息，不点击回调按钮、不访问短链或第三方跳转站。

## Unraid 部署

将本项目源代码放到 Unraid 的一个目录，例如 `/mnt/user/appdata/sbtg2cloud-src`。源码目录和运行数据目录请分开。以下在 **Unraid 终端**执行。

### 方式一：Docker Compose

需要 Unraid 已有 Docker Compose 命令（可通过 Compose Manager 使用）。

```sh
cd /mnt/user/appdata/sbtg2cloud-src
cp .env.example .env
```

编辑 `.env`，将 `BIND_IP` 改为 Unraid 的实际局域网 IP，确认 `APPDATA_PATH`。默认以 Unraid 的 `nobody:users`（99:100）运行。

```sh
install -d -m 700 -o 99 -g 100 /mnt/user/appdata/sbtg2cloud
docker compose up -d --build
docker compose logs --tail=100
```

浏览器打开 `http://你的Unraid局域网IP:8080`。未设置 `.env` 时端口默认绑定所有网卡，建议明确设置 `BIND_IP`。此服务没有管理密码，不做公网端口映射。

### 方式二：Unraid 自带 Docker，无需 Compose

```sh
cd /mnt/user/appdata/sbtg2cloud-src
install -d -m 700 -o 99 -g 100 /mnt/user/appdata/sbtg2cloud
docker build --platform linux/amd64 -t sbtg2cloud:local .
```

在 Unraid Docker 页面“添加容器”，填写：

| 项目 | 值 |
| --- | --- |
| 名称 | `sbtg2cloud` |
| Repository | `sbtg2cloud:local` |
| Network Type | `bridge` |
| WebUI | `http://[IP]:[PORT:8080]` |
| 端口 | 容器 `8080` → 主机 `8080`，TCP |
| 数据路径 | 容器 `/data` → 主机 `/mnt/user/appdata/sbtg2cloud`，读写 |
| Extra Parameters | `--user 99:100 --restart unless-stopped --security-opt no-new-privileges:true --cap-drop ALL` |

镜像包含健康检查。数据目录应只允许服务用户和管理员访问。

## 仅 Telegram 使用代理，光鸭直连

推荐部署方式为 **Telegram 走 HTTP CONNECT 代理，光鸭直连**。仅支持 HTTP CONNECT；没有实现或验证 SOCKS5、SOCKS4、MTProxy，也不接受 `https://` 代理协议。未填写 Telegram 代理地址时，Telegram 也保持直连。

在项目 `.env` 中按需填写（示例主机需自行替换，不要提交真实地址或密码）：

```env
TELEGRAM_PROXY_URL=http://proxy.example:8080
```

- `TELEGRAM_PROXY_URL` 显式传给 Telethon；不配置则 Telegram 直连。它不读取 `HTTP_PROXY`、`HTTPS_PROXY` 或 `NO_PROXY`。
- Compose 明确清空容器内的 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 及对应小写变量，并设置 `NO_PROXY=*`、`no_proxy=*`，保证光鸭 HTTPX 请求直连，避免 Docker 客户端的默认代理设置影响光鸭。无需在 `.env` 中配置这些通用代理变量；旧 `.env` 若有这些配置可以删除，当前 Compose 不再引用它们。
- `NO_PROXY` 不影响 Telethon，所以光鸭直连不会绕过 Telegram 的显式代理。本示例使用 `*` 表示全部 HTTP 请求直连，不依赖 CIDR 网段匹配能力。
- 建议显式填写代理端口；Telegram 未指定端口时默认 8080。
- 带认证时使用 `http://用户名:密码@主机:端口`。用户名、密码必须非空；`@`、`:`、`#`、`%` 等特殊字符按 URL 规则编码，例如 `http://user%40domain:p%40ss%3Aword@proxy.example:8080`。若 Compose `.env` 的值含字面 `$`，使用单引号包裹该值，避免变量插值。

Compose 只从 `.env` 读取 Telegram 代理地址，代理设置仅作用于 **sbtg2cloud 这一个容器**，不更改宿主机或其他容器。不要把真实代理地址写入源码或 Dockerfile。在 Unraid Docker 模板部署时，添加 `TELEGRAM_PROXY_URL`，将通用代理变量（含小写及 `ALL_PROXY`）清空，并设置 `NO_PROXY=*`、`no_proxy=*`，效果相同。

升级代码/依赖后执行：

```sh
docker compose up -d --build --force-recreate sbtg2cloud
```

只修改代理环境变量时也必须重建容器，单纯 `docker restart` 不会加载新环境。原 `/data` 挂载保持不变；不要删除会话、重置数据库或同时启动第二个实例。

配置错误会在 WebUI 显示具体字段及原因，不回显 URL 或认证信息；不会悄悄改为直连。普通连接失败按原有间隔每 10 秒重试。Telethon 有时会把底层超时/代理握手异常归并为通用连接错误，此时页面会说明正在通过 HTTP 代理连接，并提示检查可达性、CONNECT 支持和认证，不能保证总能精确判别 407 或超时。SDK 原始日志已禁用，避免协议请求或异常携带敏感数据；页面只显示经过处理的固定错误提示。

验证范围：测试覆盖无代理、HTTP 代理、百分号编码认证、非法配置、失败后重试、HTTPX 环境代理和精确 `NO_PROXY` 匹配，并用本地 HTTP CONNECT 服务验证 PySocks 实际握手及认证。用户现场报告已验证原会话恢复连接、光鸭目录和既有配置/历史保持不变；本次未访问现场代理，也未用新分享验证完整自动转存链路。

## 初始化

1. 打开 [my.telegram.org/apps](https://my.telegram.org/apps)，申请自己的 Telegram 应用，填写 **API ID / API Hash**。这是应用凭据，不是 Bot Token；扫码登录也需要它们。
2. 在管理页保存凭据，生成 Telegram 二维码，通过手机 Telegram 的“设置 → 设备”扫码。如账号启用两步验证，输入密码完成登录。密码不落盘；二维码过期后手动重新生成。
3. 生成光鸭二维码，用光鸭 App 扫码授权。登录令牌会自动续期，失效时重新扫码。
4. 选择默认保存目录；点击“编辑监听 → 获取聊天列表”，勾选频道、配置目录，然后点击“保存监听”。保存后仅显示选中频道，再次点击“编辑监听”可修改；取消会丢弃本次未保存的选择。
5. 等待选中频道发布新的测试分享，在记录中检查“云端处理中 → 已完成”，再去光鸭核对目标目录。

不会回溯旧消息，可在已加入且有发言权限的测试群中发布自己拥有的小文件分享，测试正文、按钮和提取码三种形式。目录选择器选择现有云盘目录；需要新目录时先在光鸭中创建。

转存记录优先显示消息中的资源名称，缺少时使用分享的文件/文件夹名称；一条消息有多个不同分享时分别使用各分享文件名。旧版记录没有保存片名，可点击“补全本页名称”读取原分享名称，此操作不会重新转存；失效或无法访问的分享暂不能补全。

转存记录默认每页 20 条，可选择 10、20、50、100 条，通过上一页、下一页或输入页码跳转。修改每页数量会返回第一页。“最新记录”返回第一页并获取新任务；浏览后续页时固定记录范围，避免新任务插入导致翻页重复或漏项，任务状态仍会刷新。

点击顶部“待处理”会跳转至转存记录并筛选排队任务；点击“需要处理”会筛选失败和结果待核对的任务。筛选覆盖全部记录，支持分页和自动刷新；通过记录区域的“记录筛选 → 全部记录”恢复查看。筛选中的任务状态变化后会移出或加入对应列表。

## 更新现有部署

用新版源码覆盖旧源码目录，保留 `.env` 和原 `/data` 挂载。Compose 部署执行 `docker compose up -d --build`；Unraid 模板部署重新执行 `docker build --platform linux/amd64 -t sbtg2cloud:local .` 后，在模板编辑页面应用配置以重建容器。仅重启旧容器不会换成新镜像。

新版本启动时自动添加资源名称字段，保留原登录、监听配置、任务和去重记录。建议更新前停容器并备份数据目录。

## 数据与恢复

`/data/state.sqlite3` 保存配置、光鸭令牌、来源和任务；`/data/telegram.session` 保存 Telegram 会话。它们是敏感登录凭据，不要上传到 Git、日志或公开聊天。备份前停止容器，并备份整个 `/data`（包含可能的 SQLite WAL 文件）。

任务状态：`queued` 排队、`preparing` 读分享、`submitting` 提交中、`submitted` 云端处理中、`success` 完成、`failed` 失败、`uncertain` 结果待核对。

- 修改目录只影响之后入队的任务；任务保存入队时的目标目录快照。
- 停用来源只停止接收，不取消已入队任务。
- 若在提交请求中途崩溃/超时，恢复后显示“结果待核对”，避免重复转存。检查云盘确定未转存后再重试。
- 云端任务明确失败时，先核对是否部分文件已保存，再手动重试；同名文件如何处理由光鸭服务决定，本项目不会主动删除或覆盖已有文件。
- 退出 Telegram 仅注销本项目会话，并停用来源，不注销手机等其他设备。
- 当前按单 Telegram 账号和单光鸭账号使用；更换光鸭账号前应停止监听并处理完队列，因为现有目录 ID 属于原账号。
- Telegram 消息时间戳精度为秒，启用/恢复监听同一秒的边界消息可能被接收，不扫描历史接口。

## 转存成功一小时后自动清理

管理页面底部提供“自动清理”开关，默认关闭。资源直接保存到你选定的目录，不创建额外的 `sbtg-*` 子目录。原监听配置和去重记录保留。

- 以本地 `completed_at`（确认云端转存成功的时间）为准，满 3600 秒后才允许清理。每 30 秒只查本地数据库，每轮最多处理一个任务；重启继续原计时。关闭开关暂停未提交的删除，已提交的删除无法撤回。
- 转存前记录目标目录已有 ID 和分享顶层条目的名称、类型、大小；成功后仅匹配本次新增且与分享条目一致的 ID。已有同名资源、合并、重命名或匹配不唯一时，保留转存结果并停止自动清理。不会删除选定的保存目录或其中原有资源。
- 为目标记录内容快照，到期后核对位置、名称和内容再删除。操作期间不要由其他程序同时新增同名资源或修改目标；云盘没有已核实的原子条件删除接口，核对与删除之间仍有并发修改窗口。
- 普通文件或文件夹移入回收站，不清空回收站。删除超时、回执缺失或提交中重启时停止重发；有任务 ID 时只查询原任务。同一目标 ID 登记到单个清理任务，防止重复删除。
- 旧版已经生成的空 `sbtg-*` 目录不会继续作为重试的保存位置，也不会擅自删除。旧临时目录有内容时阻止重试，先核对资源；已经完成的旧任务保持原位置，不自动迁移内容。

历史成功记录没有 `completed_at` 时，按 `当前时间 - created > 7200 秒` 判断到期，不使用 `updated`。在“历史记录清理”中选定对应的实际文件或文件夹后，后台按该规则核对并移入回收站；仅处理成功任务。由于旧记录没有保存目标 ID，需要先选定目标，不能仅凭同名自动绑定。失败、未到期、未匹配或尚未选定目标的任务不会删除。开关关闭时已加入的清理任务暂停。同一文件 ID 只允许加入一次，删除失败或回执不明不会再次提交。

历史列表采用纵向卡片，显示创建时间、两小时到期时间、原目录、候选名称和 ID。未到期任务不请求云盘；到期候选列表仅在点击时加载，同目录缓存 5 分钟。真正删除前重新核对，不使用缓存。

所有光鸭请求在单进程内串行发送，每次请求结束后至少间隔 2 秒；HTTP 429/5xx 至少冷却 60 秒，数字形式 `Retry-After` 按 60～900 秒处理。转存首次进度查询等待 15 秒，未完成时每 30 秒查询；删除进度最多每 60 秒查询一次（首次等待 30 秒）。页面常规状态刷新只读取本地状态。限速不能保证规避平台未公开的风控，请控制监听数量与任务量，保持单实例运行。

此功能已通过模拟协议测试，尚未用真实账号执行删除验证；默认保持关闭，先使用专门的测试资源验证转存、到期和回收站结果。

对于已经逐项确认的历史目录，提供独立工具 `scripts/cleanup_confirmed.py`。确认清单 JSON 使用 `{"version":1,"targets":[{"id":"目标目录ID","name":"目录名称","parent_id":"原父目录ID"}]}`，只支持目录。必须先停止主容器，使用同一数据卷运行，默认只读核对，显式传入 `--execute` 才整批移入回收站。工具使用实际目录 ID 与名称核对，不猜测历史成功时间；回执保存在 `/data/confirmed-cleanup.sqlite3`。相同清单再次执行只查原任务或报告原结果，出现部分重叠的新清单也会阻止重复删除。切勿删除该日志后重跑。操作期间不要同时在其他设备移动或删除目标目录。确认清单、执行日志和真实数据不得上传 GitHub。

## 本地开发及测试

Python 3.12：

```sh
python -m venv .venv
# 激活虚拟环境后
pip install -r requirements.txt
python -m unittest discover -s tests -v
uvicorn app.main:app --host 127.0.0.1 --port 8080 --no-access-log
```

Windows 可使用 `.venv\Scripts\python.exe`。默认本地数据目录 `./data`，可用 `DATA_DIR` 覆盖。必须单 worker 运行，不能启用多个 Uvicorn worker 或同时运行共享 `/data` 的容器。

## 验证范围与限制

已通过模拟协议测试验证分页、令牌续期、去重、队列恢复、重试边界、来源过滤和 Web API 基础防护。已匿名实测光鸭生成二维码与等待授权的 OAuth 响应；实际账号扫码、转存、同名冲突仍须部署后联调。开发环境没有 Docker 引擎，因此本机未构建/启动容器；部署文件以 `linux/amd64` 为目标。

光鸭接口依据当前官方网页前端和公开实现核实，不是官方承诺稳定的第三方 API；发生变化会明确显示失败，不会假报成功。详细证据见 [docs/INTEGRATION.md](docs/INTEGRATION.md)。
